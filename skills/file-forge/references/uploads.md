# Project upload workflow

Verify installed help/tool schemas first. Built-in project uploads use `check_upload_config`, `plan_upload`, `upload_files`, `verify_upload`, or CLI `upload config check|plan|apply|verify`. Upload-only work needs Node.js, not FFmpeg/Chrome. Never substitute a custom curl/SDK upload to bypass this workflow.

Require an exact project key; never infer from directory, domain or chat preference. The user maintains private `file-forge.upload.local.json`, selected by host `FILE_FORGE_UPLOAD_CONFIG` or the documented configuration default. MCP cannot override that path. Never open, paste, edit, migrate, export or back up the real file. First run the sanitized offline check for the exact project; with MCP, poll the check job to terminal success. Do this before inspecting or generating test assets, hashing inputs, planning, or applying. If blocked, stop and ask the user to configure the private JSON locally and say when to recheck. On missing/invalid config, explain the field/protection repair, recommend local user editing, and ask for a decision. Do not ask for credentials in chat. This is plaintext storage, not encryption.

Config is a flat project map. Each entry requires CONFIG_VERSION=1, R2_ENDPOINT, R2_BUCKET, R2_REGION=auto, R2_PUBLIC_BASE_URL, FILE_PATH, R2_ACCESS_KEY_ID and R2_SECRET_ACCESS_KEY. All but version are strings. Empty FILE_PATH means bucket root; nonempty prefixes end in slash. No teams, defaults, environment inheritance or automatic bucket/domain discovery. Keep the file outside runtime, rollback, skill and delivery directories; private owner permissions and Git exclusion/untracked status are required. Users migrate old values privately and choose flat keys explicitly.

Plan before execution. CLI: `file-forge upload plan --project KEY --input PATH --output EXISTING_PARENT [--recursive] [--overwrite-key EXACT_KEY] --json`. MCP: `plan_upload` with operation upload-plan, project, input, output, recursive, optional overwriteKeys, and requestId. Directories require explicit recursion. Plans include every selected file, hash, size, MIME, bucket/key/URL and replacement intent, plus exclusions. Review authenticity, page/section placement, prompts, naming and appropriateness yourself; generic transport does not know business semantics.

Show mappings and obtain explicit upload authorization. Approval for local organization, uploads, replacing historical objects and website-link edits are separate. Reuse unchanged explicit authorization. Changed contents/destinations need a new plan/review. A plan hash or apply flag is integrity binding, not proof of approval. Do not add timestamps/project names to keys or normalize filenames. Existing processed outputs can be selected; manifests, logs, prompts, secrets and control files are not assets. Cover/poster processing must already satisfy the image workflow; upload does not re-encode.

Execute only the approved plan/digest: `upload apply --project KEY --plan FILE --plan-hash SHA256 --json`, or upload_files with operation upload-apply, project, plan, planHash and requestId. Create-only is default; review exact overwriteKeys during planning for replacements. No global overwrite switch, retry, automatic remote rollback, cache purge, deletes or code-link updates. A batch is not a transaction.

Poll job_status; retain the plan, execution marker and receipt. Unknown jobs after reconnect do not establish absence. A recorded expected receipt path may not yet exist. Uploaded and public HEAD results differ; HEAD cannot prove byte integrity or cache freshness. Sending/unknown outcomes may already have committed. Stop on failure, explain evidence and a concrete recovery proposal, then ask before new writes. Never delete an execution marker or replay a plan to recover.

Use `upload verify --project KEY --receipt FILE --json` or verify_upload (upload-verify) for read-only reconciliation when authorized. It records matches/differs/absent_observed/unknown; a negative read does not prove an in-flight write failed. Create a new reviewed plan for remaining work. Clean only task-owned temporary resources; preserve original assets, execution records and completed remote objects. Append an existing project delivery log only when authorized by that project's workflow, and never include secrets. Remote acceptance tests and cleanup need specific authorization.

CLI upload progress shows per-file and byte-weighted overall percentages on stderr (also with `--json`). 100% means the body was supplied to the HTTP transport, not R2 confirmation. Wait for the confirmed upload result; public URL checks remain separate and can produce a partial result.

CLI `upload apply` supports `--progress auto|table|lines`. The default `auto` uses a live table in terminals at least 79 columns wide and 10 rows tall; pipes, narrow terminals and `TERM=dumb` use lines. The table separates sent percentage, R2 confirmation and public URL results, with byte-weighted overall progress. Live tables show up to eight recent files; the final table includes all receipt entries. Object keys are escaped and clipped for safe display; full keys remain in the JSON result and receipt. Explicit `table` in redirected or small-terminal output prints plain snapshots without cursor controls. All progress stays on stderr, including with `--json`.

For a read-only folder inventory, check the exact project configuration first. Run `upload folders --project KEY [--prefix SUBFOLDER] [--json]` or submit `list_bucket_folders` with operation `upload-folders`, project, requestId and optional relative prefix. Poll the MCP job to completion. The tree starts at FILE_PATH and includes folders implied by current object keys and explicit folder markers. A limit error means the user should select a narrower subfolder.
